# Candor Design System

**Version 4.1 · June 2026**

Candor is a design system built on a single premise: *good design tells the truth about what works.* Passing a checklist and working for people are different achievements. The system is built around the second one — for the widest range of people, in the widest range of contexts.

Candor is a commitment to close the gap between nominal compliance and outcomes that work.

---

## Design Principles

### Accessibility is the baseline, not the finish line
WCAG compliance is where we start. Outcome-based validation — real color science, real user impact — is where we go from there. Every token, every component, every contrast decision is validated using OKCA — a contrast algorithm that addresses known issues with WCAG's luminance math while prioritizing WCAG compatibility and coherence with OKLCH, so designers can directly equate their color pickers and tonal ramps with accessibility outcomes.

### Perceptual truth over nominal correctness
Colors are defined in OKLCH — a perceptually uniform color space where equal numeric changes produce equal perceived changes. This isn't an aesthetic preference; it's what makes programmatic accessibility validation reliable.

### Typography as cognitive infrastructure
The typographic system is organized around two human modes: **execution** (task completion, navigation, scanning) and **interpretation** (reading, reflecting, conversing). Font choices aren't decorative — they signal which mode a surface is designed for.

### No hard-coded values, ever
All styling flows from design tokens. Components never reach past their token layer. This isn't a rule for tidiness — it's what makes the system auditable, adjustable, and honest about its own decisions.

## Color Philosophy

The palette draws from personal brand anchors — deep navy (`#082840`), warm burgundy (`#5F2B48`), and azure (`#1493FB`) — extended into a full OKLCH token system. Two-tier architecture keeps the system honest: primitives are raw tonal ramps, semantic tokens map those ramps to roles. Components reference semantic tokens only — never primitives directly.

Every semantic color pair has a documented contrast validation against its intended background. The validation methodology is in the next section.

## Component Events

Components communicate outward through DOM `CustomEvent`s. Every Candor event is dispatched with `bubbles: true, composed: true`, so it crosses the shadow boundary and reaches listeners on light-DOM ancestors.

**The naming follows the DOM's own two-event rule**, applied uniformly so there's nothing component-specific to memorise:

- **`change`** — the *committed* value. Every value control emits it: input, autocomplete, select, radio, checkbox, switch, slider, listbox, combobox, and chip. This is the predictable event to reach for. Discrete controls (checkbox, radio, select, switch) commit in a single action, so `change` is the only value event they emit — exactly like their native counterparts.
- **`input`** — the *live, mid-edit* value, fired continuously. Only controls with a real editing phase emit it: `candor-input` (per keystroke), `candor-autocomplete` (per free-text keystroke), `candor-slider` (per drag tick / arrow step), and `candor-combobox` (per filter-text keystroke) — mirroring native `<input>` and `<input type="range">`.

Semantic, non-value events keep distinct names: `send`, `dismissed`, `closed`, `selected`, `toggle`, `clicked`, `page-change`, `tab-change`, `color-select`, `cell-activate`.

Event names and their `detail` types are published in the `@candor-design/web-components` TypeScript declarations — import a `*Detail` type or a per-component `*EventMap` interface instead of hand-annotating:

```ts
import type { CandorSelectChangeDetail } from '@candor-design/web-components';

el.addEventListener('change', (e) => {
  const value = (e as CustomEvent<CandorSelectChangeDetail>).detail; // string
});
```

**Deprecated aliases.** Three controls previously used bespoke value-changed names. Each legacy name is still emitted with its original semantics so existing listeners keep working, and maps to whichever new event shares those semantics. The aliases are deprecated and will be removed in the next major.

## Styling & overriding

Design tokens (`--color-*`, `--font-*`, `--spacing-*`) pierce the shadow boundary automatically, so re-theming the whole system is just a matter of setting token values. But tokens are global — they can't reach *one* component's internals. For that, Candor exposes two per-component hooks. Both are **opt-in**: set nothing and the component renders from its tokens exactly as before.

**1. Custom properties — the blessed density/shape knobs.** Named `--candor-<component>-<knob>`, each defaults to the existing token, so overriding one nudges a single dimension without forking. Reach for these first — they're a supported, stable API and don't depend on internal structure.

```css
/* Go denser than size="small" without re-implementing the button */
candor-button { --candor-button-min-height: 1.75rem; --candor-button-padding-y: 0.25rem; }

/* Match an input's corner radius to a tighter surrounding form */
candor-input { --candor-input-radius: var(--radius-sm); }
```

**2. `::part` — the escape hatch for arbitrary restyle.** Meaningful internals carry a `part` name, so any CSS property is reachable from the light DOM when there's no custom property for it.

```css
candor-button::part(button) { letter-spacing: 0.03em; text-transform: uppercase; }

/* The classic "disclosure is the first child of a padded box" fix (#173):
   kill just the top padding, which no single density knob can express. */
candor-disclosure::part(trigger) { padding-top: 0; }
```

**Rule of thumb:** a custom property when there's a bounded design intent (density, radius); a part when you might do anything. Part names and custom-property names are **public API** — additions are minor releases, renames/removals are major.
